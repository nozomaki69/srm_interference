# CFAR 干渉検知：設計と作業記録

`script/detect_cfar.py` の設計判断・実験結果・未解決事項の記録。
ブランチ `cfar_detection`（`correct_mesure` 起点）での作業。

---

## 1. なぜ作ったか

`analyze_csv.py` の `evaluate_interference_detection()` は、`interf` と `no_interf`
**両方のラベルを見て F1 を最大化する τ** を選んでいる。実運用では「干渉あり」の
ラベル付きデータは手に入らないため、これは達成不能な上限（genie-aided）である。
国際会議の査読では "threshold tuned on test data" として確実に指摘される。

さらに F1 には構造的な下限がある。τ を 0 まで下げると全 seed が陽性になるので

```
precision = n_pos/(n_pos+n_neg),  recall = 1  ->  F1 = 2*n_pos/(2*n_pos+n_neg)
```

100 対 100 なら **0.667**。F1 を最大化して τ を選ぶ以上、分離が全くできていない
条件でも F1 は必ずこの値以上になる。実データでは 1200 セル中 **121 セル (10.1%)**
がここに張り付いていた。

## 2. 定式化：2クラス分類ではなく片側検定（CFAR）

自組織が観測できるのは H0（自PAN単独・干渉なし）だけで、H1（干渉あり）は観測できない。
したがって閾値は目標誤警報率 α から定める（CFAR: Constant False Alarm Rate）。

### 統計量の自己正規化

無干渉時の統計量の水準は、ほぼ全部が PER 推定の二項ノイズで決まる。
デバイス i・方向 d について

```
v_i,d = p_d(1-p_d) / N_i,d
```

`N` は `macTxSuccessCount + macRetryCount + macMultipleRetryCount + macTxFailCount`、
`p̂` は `macTxFailCount / N`。**いずれも IEEE 802.15.4 の MIB 変数そのもの**なので、
自組織だけで計算できる（実機適用性の根拠にもなる）。

これにシャドウイングとビン幅に由来する不均質 `σ²_het` を足したものが、
ビン内分散の期待値になる。

```
E[s2_b] = vbar_b + σ²_het
Z_b     = s2_b / (vbar_b + σ²_het)
T_norm  = max_b Z_b
```

### 設計量を3つに分ける

「全動作点をカバーする」のではなく、**判定できる領域を自分で宣言し、その中で確実に
判定する**方針にした。これに伴い設計量が3つに分かれる。

| 設計量 | 意味 | 用途 |
|---|---|---|
| α | 目標誤警報率 | **τ を決める（これだけ）** |
| Δ | 最小検知対象干渉強度（感度仕様） | 有効領域を決める |
| 1−β | 目標検知率 | 有効領域を決める |

τ を動作点ごとに動かして無理に性能を揃えるのではなく、**τ は α から素直に決め、
検出力が足りない動作点は判定を保留する**。

### 運用時の手順（すべて自PANの観測量のみ）

```
1. 自MACカウンタから vbar = mean_i[p̂_dl(1-p̂_dl)/N_dl + p̂_ul(1-p̂_ul)/N_ul]
2. 帰無スケール S0 = vbar + σ²_het        (σ²_het は自PANの H0 較正値)
3. 検出力 = 1 - Π_b F_chi2( (m_b-1) * τ_α * S0_b/(S0_b+Δ) )
4. 検出力 >= 1-β なら判定、未満なら保留 -> 観測窓を延長
5. 判定は T_norm >= τ_α
```

3 で使うのは vbar（自分で測れる）、σ²_het（自分の H0 から較正）、Δ（自分で決めた仕様）
だけで、**干渉源の情報は一切使わない**。Δ は「これ以上の干渉なら検知したい」という
仕様であって、実際の干渉強度の知識ではない点が重要。

## 3. 較正と評価の分離

| | 用途 | 使うデータ |
|---|---|---|
| 較正 | σ²_het, τ_α | **`no_interf` の seed 0–49 のみ** |
| 評価（FPR） | 実現誤警報率 | `no_interf` の seed 50–99 |
| 評価（TPR） | 検知率 | `interf` の全 seed |

`calibrate()` は `label == "no_interf" and seed < train_seeds` でフィルタした
データしか受け取らず、`interf` を関数内で一切参照しない。

## 4. σ²_het の決め方（方針変更あり）

当初は積率法（`E[s2] = vbar + σ²_het`）で推定する設計だったが、**単体テストで
系統的な過小推定を確認したため方式を変えた**。

| 真値 | N | p | m | 積率推定 | 比 |
|---:|---:|---:|---:|---:|---:|
| 0.0025 | 48 | 0.30 | 6 | 0.00000 | 0.00 |
| 0.0025 | 500 | 0.30 | 6 | 0.00192 | 0.77 |
| 0.0100 | 48 | 0.30 | 6 | 0.00514 | 0.51 |

二項ノイズ `vbar` が `σ²_het` より大きい領域（まさに今回の動作点）で崩れる。原因は
ΔPER が離散的で標本分散の χ² 近似が小標本 (m≈6) で成り立たないことと、
`vbar` 自体が同じ標本から推定した誤差を持ち、平滑化 `(F+0.5)/(N+1)` により
低 PER 側で上振れすること。

そこで σ²_het を「真値を当てる量」ではなく**調整パラメータ**と割り切り、
**H0 における (1−α_ref) 分位点が動作点（自PAN伝送速度 × 自PAN負荷）を跨いで
一定になる**ように選ぶ方式にした（`fit_sigma2_het_invariance()`）。
これは「単一の τ を条件横断で使える」という主張そのものが最適化基準になるので、
積率推定の偏りに悩まされない。**参照するのは H0 のデータだけ**なので自己決定性は保たれる。
積率推定値は診断値として併記する（`sigma2_het_moment`）。

## 5. 実データでの結果（120,000 ラン、学習 59,970 観測）

### 安全側には動いている

| 設計 α | 実現 FPR 中央 | 実現 FPR 平均 | TPR 中央 |
|---:|---:|---:|---:|
| 0.01 | 0.000 | 0.0045 | 0.200 |
| 0.05 | 0.040 | 0.0345 | 0.450 |
| 0.10 | 0.080 | 0.0778 | 0.590 |

実現 FPR は全て設計 α 以下。誤警報が設計値を超えることはない。

### 問題：低負荷側で過度に保守的

α=0.05 での実現 FPR（自PAN速度 × 自PAN負荷、中央値）:

```
own_kbps \ own_offload   20    40    60    80   100   120   140   160   180   200
    50                 0.00  0.00  0.00  0.06  0.10  0.04  0.00  0.12  0.06  0.06
   100                 0.00  0.00  0.02  0.07  0.01  0.03  0.04  0.05  0.07  0.07
   200                 0.00  0.00  0.00  0.00  0.04  0.02  0.04  0.04  0.06  0.08
```

自負荷 20–40% では全速度で FPR = 0。単一 global τ が動作点差を吸収できておらず
（`quantile_cv_across_operating_points = 0.311`、合成データでは 0.056）、
誤警報を出さない代わりに検知もできていない。

### oracle との比較

oracle の FPR が 0.02–0.08 の 263 条件での直接比較:

| | TPR 中央 | FPR 中央 |
|---|---:|---:|
| oracle（genie-aided, 上限） | **0.910** | 0.040 |
| CFAR（α=0.05, H0のみ） | **0.657** | 0.000 |

検知可能領域（相手負荷 ≥ 80%）での Youden J は oracle 0.685 / CFAR 0.500。
CFAR は oracle の J の約 73% を保持している。FPR が 0.000 に張り付いていることから、
**差の大半は統計量の性能ではなく較正の過保守に起因する**。

### 物理的に意味のある傾向

TPR は自負荷とともに単調低下（50 kbps で 0.58@20% → 0.354@200%）。
自PAN の輻輳が自前の PER 変動を増やし、干渉由来の変動を覆い隠すため。

## 6. 検出力の理論（設計上もっとも重要な発見）

1ビン単独の検出力（α=0.05、`Z_b` は H0 で `χ²_{m-1}/(m-1)`）:

| ビン内端末数 m | τ | Δ=1·S0 | Δ=2·S0 | Δ=3·S0 | Δ=5·S0 |
|---:|---:|---:|---:|---:|---:|
| 6 | 2.214 | 0.354 | 0.595 | 0.736 | 0.870 |
| 10 | 1.880 | 0.489 | 0.775 | 0.896 | 0.971 |
| 15 | 1.692 | 0.619 | 0.895 | 0.968 | 0.996 |
| 30 | 1.467 | 0.849 | 0.990 | 0.999 | 1.000 |

実測の global τ = 2.147 は m=6〜7 相当で理論値と一致する。

**現状は 30 台を 10 dBm 幅で 4〜5 ビンに割るため m ≈ 6 しかなく、検出力 0.8 を得るのに
Δ = 5·S0 もの干渉が必要。τ の微調整よりビン幅のほうが遥かに効く。**

### ビン幅のトレードオフ

```
ビン幅を広げる -> m 増（検出力↑）だが σ²_het 増（S0↑ -> Δ/S0↓ で検出力↓）
```

較正値 σ²_het = 0.0128 は生の統計量スケール（oracle τ が 0.015〜0.04）に対して大きく、
**観測窓を延ばして vbar→0 にしても S0 は σ²_het で頭打ち**になる。窓延長だけでは
限界があり、ここが高負荷で判定が難しくなる本質と考えられる。

したがってビン幅には最適値があり、「検出力を最大化する」という明確な基準で決められる。
現在の「10 dBm 幅・最弱端 5 dBm 切り捨て」は根拠が弱く査読で突かれる箇所だったが、
これを原理的な決め方に置き換えられる。

## 7. 実装

### サブコマンド

```sh
# 生データ -> RSSIビンごとの統計量（重い。ビン幅を変えるとき以外は1回だけ）
python3 script/detect_cfar.py extract [--bin-size 10] [--n-min 0]

# 較正 + 評価（出力は scope ごとに別ファイル）
python3 script/detect_cfar.py run --scope global     [--delta 0.02] [--target-power 0.8]
python3 script/detect_cfar.py run --scope own_config [--delta 0.02] [--target-power 0.8]
```

- `extract` の出力 `plots/bin_statistics.csv` は実データで約 100 MB。
  GitHub の 1ファイル 100 MB 制限に当たるため `.gitignore` 済み。**scp で運ぶこと**
- `run` の出力は `plots/cfar_results_{scope}.csv` と `plots/cfar_calibration_{scope}.json`

### scope の意味

- `global` … 全条件で単一の τ。最も強い主張になるが、上記のとおり過保守
- `own_config` … 自PAN伝送速度 × 自PAN負荷ごとに τ。自組織は自分の設定を
  知っているので**自己決定性は損なわれない**。学習標本は 59,970/30 ≈ 2,000 観測/層 で
  α=0.01（目安 1,000）にも足りる

### 実装上の注意

- 分位点は `method="higher"` で保守側に取る。補間すると τ が小さくなり実現 FPR が
  設計 α を上回りやすい
- 目標 α に対し学習標本が `10/α` 個を下回る場合は警告を出す
  （標本 50 個で 99 パーセンタイルは決められない）
- ビンの切り方 `select_bins()` と干渉ラベル判定は `analyze_csv.py` から import する。
  複製すると定義が2箇所に増えて必ずずれる
- 出力の既定パスは `SCRIPT_DIR` 相対（`analyze_csv.py` 等と同じ規約）。
  scope を含めた名前にしてあり、scope 違いの連続実行で上書きされることはない

## 8. 検証したこと

- **`detection_power()`** … m と Δ/S0 を振って χ² の理論値と突き合わせ、
  12 通りすべてで小数4桁まで一致
- **`estimate_sigma2_het_moment()`** … 真値既知の合成ビンで偏りを定量化（§4 の表）
- **pipeline 全体** … 正解を埋め込んだ合成 `simulation_results.csv`
  （`no_interf` と `interf` を作り分け）で end-to-end 実行し、
  実現 FPR が設計 α に追随することを確認（α=0.05→0.02、α=0.10→0.10）

## 9. 同時に入れた修正

- **`analyze_csv.py`** … 距離の基準ノードの取り違え。PAN1 のデバイスを id=2、
  PAN2 のデバイスを id=1 基準で距離計算していた（生成側は PAN1 Co=id 1, PAN2 Co=id 2）。
  影響は `pan*_errorbar_*.pdf` のみで、干渉判定は距離を使わないため結果に影響なし
- **`create_heatmap.py`** … カラーバー下限を 0.5 から F1 の構造的下限
  （`2*n_pos/(2*n_pos+n_neg)`）に変更し、下限に張り付いたセルを灰色でマスク。
  比較は丸めた下限に対して行う（`analyze_csv.py` が F1 を小数3桁に丸めるため、
  生の下限 0.6667 と比べると 0.667 が判定から漏れる）

   領域内での TPR ヒートマップ

### Δ の決め方について

Δ は運用者が与える仕様だが、論文では `interf` ランから
「Δ 仕様 → カバーされる干渉源負荷」の対応表を作って裏付ける必要がある。
これにより「Δ = 0.02 と設計すれば、干渉源負荷 80% 以上をカバーできる」といった
運用上意味のある記述ができる。
