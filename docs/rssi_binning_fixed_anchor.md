# RSSI ビンの起点を固定値にする（`fixed_anchor_bins`）

`one_side_correct_measure` を起点に、RSSI ビンの下端を**チャネル固有の固定値**に変えた
ブランチ。ビン幅 10 dBm と、上方向に刻む点は従来どおり。

---

## 1. 何を変えたか

```
旧: 起点 = そのSeedの実測RSSIの最小値 + 5 dBm     ← データ依存
新: 起点 = 受信感度(チャネル固有) + 5 dBm          ← 固定
```

実装は `script/analyze_csv.py` の `bin_anchor_dbm()` と `select_bins()`。

| ch | kbps | 受信感度 | 起点 | 第1ビン |
|---:|---:|---:|---:|---|
| 0 / 3 | 50 | −97.0 | −92.0 | (−92.0, −82.0] |
| 1 / 4 | 100 | −93.99 | −88.99 | (−89.0, −79.0] |
| 2 / 5 | 200 | −90.98 | −85.98 | (−86.0, −76.0] |

**捨てる幅 5 dBm の意図は変わっていない。** 基準が「実測最小値」から「受信感度」という
固定値に変わっただけである。セル端は PER が 0.5 付近になり二項ノイズ p(1−p)/n が
最大になるため、干渉が無くても端末間のばらつきが大きく出て誤検知の床を決めてしまう、
という統計量 A′ の理由づけはそのまま残る。

## 2. なぜ固定値にするか

データ依存の起点では、負荷や帯域で RSSI 分布が少しずれるだけでビン境界と端末の
切れ方が変わり、**「同じリングの端末どうしを比べる」という指標の前提がぶれていた**。
受信感度はチャネルごとの固定値なので、起点をここに置けばビン境界が Seed にも負荷にも
依存しなくなる。

ビン位置がチャネルごとに違うこと自体は問題にならない:

- 判定は各 PAN が自分のデータだけで行うので、他 PAN と絶対値を揃える必要がない
- `interf` と `no_interf` の対（ch0↔ch3、ch1↔ch4、ch2↔ch5）は周波数だけが違い、
  受信感度は同一なので、対比較の中ではビン定義が完全に一致する。
  `run_interference_detection()` はこれを実行時に検査し、違っていれば例外を投げる

### ED しきい値ではなく受信感度 +5 にした理由

ED しきい値（= 受信感度 + 10 dB）を起点にする案も検討したが、同じ伝搬モデルでの
概算で受信感度 +5 が明確に優れていた。

| 起点 | 除外される端末 | 最大ビンの m | 検出力 (Δ=2·S₀, α=0.05) |
|---|---:|---:|---:|
| ED しきい値 | 約20台 | 6.9 | 0.650 |
| **受信感度 +5 dBm** | 約12台 | **12.2** | **0.834** |

ch1 / ch2 でもほぼ同じ比になる（除外 12.9 / 12.6 台、最大 m 11.8 / 12.0）。

**注意（過去の誤った説明）:** 「ED 以下 = CCA で干渉源を検知できない隠れ端末」という
根拠づけは誤り。ここで使う RSSI は `PANn_PC_RSSI_Avg_from_Dev`、つまり
**コーディネータが自デバイスから受信したときの値**であり、デバイスが干渉源を
聞けるかどうかとは別物である。正当な根拠は「固定参照レベル」であって、
隠れ端末の境界ではない。

## 3. 診断出力

起点を固定値にすると「何台が起点より上に残るか」で検出力が決まるが、その見積もりは
伝搬モデルからの概算しかできない。そこで実行のたびに実測値を出すようにした
（`print_bin_diagnostics()`）。

```
=== RSSIビンの構成 (起点 = 受信感度 + 5.0 dBm, ビン幅 10 dBm) ===
  PAN  ch  kbps       起点     観測数       受信端末/観測       起点超え/観測      割合
 PAN1   0    50   -92.00      20          30.0          18.1   60.5%
 ...
  PAN  ch     有効ビン/Seed          ビン内端末数(中央)    最大      有効ビン0のSeed
 PAN1   0          2.30                 6.0    15               0
```

**まず「起点超え/観測」と「割合」を見ること。** 概算では 30 台中 18 台（60%）、
最大ビンの端末数が約 12 を見込んでいる。大きく下回るなら
`RSSI_BIN_ANCHOR_OFFSET_DBM` を下げるか `RSSI_BIN_SIZE_DBM` を広げる。

有効ビンが1つも作れなかった観測があると警告が出る。その観測の干渉指標は 0.0 に
縮退していて検知に寄与しないため、無視できない件数なら起点が高すぎる。
件数は `interference_detection_results.csv` の
`n_degenerate_interf` / `n_degenerate_no_interf` 列にも条件ごとに残る。

## 4. 変更したもの

| 箇所 | 内容 |
|---|---|
| `RX_SENSITIVITY_DBM` | `interference_2pan_config.CHANNELS` から import して構築。`CHANNEL_KBPS` のようなローカル複製にしないのは、`create_heatmap.py:17` と同じ理由（生成側を変えたときに片方だけ取り残される） |
| `RSSI_BIN_ANCHOR_OFFSET_DBM` | 既定 5.0。ビン幅とあわせて感度解析で振る対象なので定数にしてある |
| `bin_anchor_dbm(ch)` | チャネル → 起点 |
| `select_bins()` | 第2引数に `anchor_dbm` を追加（必須）。実測最小値の参照を削除 |
| `plot_delta_per_analysis()` / `plot_variance_distribution_boxplot()` | `anchor_dbm` を引数に追加 |
| `compute_seed_max_variance()` | `anchor_dbm` と `stats_key` を追加。戻り値が `(値のリスト, 縮退Seed数)` のタプルに変更 |
| `interference_detection_results.csv` | `n_degenerate_interf` / `n_degenerate_no_interf` 列を追加 |

## 5. 検証したこと

- **`select_bins()` の単体テスト 10 件**（すべて合格）: 起点以下の除外、境界の内外判定
  （`lower < r <= upper`、−92 は除外・−82 は第1ビン）、`min_count` 未満のビンの除外と
  間が空くこと、RSSI=0 の除外、起点超えが居ないときに空を返すこと、`bin_size` の変更、
  **起点がSeedのデータに依存しないこと**
- **end-to-end**: 面積一様配置 + `RSSI(r) = −58.16 − 40log₁₀(r/154)` で実データに近い
  RSSI 分布を作った合成 `simulation_results.csv`（実ヘッダ 1037 列）で
  `load_and_aggregate()` → `run_interference_detection()` → `print_bin_diagnostics()` を通した。
  **起点超えの割合は 60.5〜64.3%** で、モデルからの概算（約60%）と一致した
- **縮退経路**: 全端末を起点以下にした条件を作り、警告が出ること・
  `n_degenerate_*` 列に正しく件数が入ることを確認

## 6. 実行方法

`create_csv.py` は変更していないので **`simulation_results.csv` の再生成は不要**。

```sh
python3 script/analyze_csv.py
```

出力ファイル名は従来と同じなので、`one_side_correct_measure` の結果と比較するなら
`plots/interference_detection_results.csv` を退避してから実行すること。

### 実データで見る順番

1. 診断の「起点超え/観測」と「割合」（概算 18台 / 60%）
2. 「有効ビン0のSeed」が無視できる件数か
3. F1 を `one_side_correct_measure` の結果と比較する。旧起点（実測最小値+5）は実際には
   −90〜−92 付近に来るので固定値 −92 とほぼ同じ位置であり、**大きくは動かないはず**。
   大きく動いたらどちらかに想定外がある、という判断材料になる
