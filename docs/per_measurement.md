# PER の測り方（`icc` ブランチ）

このブランチで PER がどう測られているかの決定版のまとめ。
実装は `script/create_csv.py`（トレース → カウンタ）と
`script/analyze_csv.py::_one_side_per()`（カウンタ → PER）に分かれている。

---

## 1. 定義

```
PER = 1 − (受信側が実際に受信したデータフレーム数)
          / (macTxSuccessCount + macRetryCount + macMultipleRetryCount + macTxFailCount)
```

分子は**受信側**の受信数、分母は**送信側**の MAC 再送カウンタ4種の和。
値は `[0, 1]` にクリップする（理由は §5）。

### 方向ごとの対応

PER は上り・下りで独立に計算する。方向によって分子・分母に使う列が変わる。

| 方向 | 意味 | 分子（受信数） | 分母（送信側カウンタの接頭辞） |
|---|---|---|---|
| **UL** | デバイス → コーディネータ | `PANn_PC_Rx_from_Dev{d}`<br>= **コーディネータが各エンドデバイスから受信した数** | `PANn_Dev{d}_to_Co_` |
| **DL** | コーディネータ → デバイス | `PANn_Dev{d}_Rx_from_PC`<br>= デバイスがコーディネータから受信した数 | `PANn_Co_to_Dev{d}_` |

この対応は、UL と DL で非対称な本数を置いた合成トレース（UL送信10 / DL送信20、
UL受信8 / DL受信15）で端から端まで検証済みであり、入れ替わりは無い。

## 2. 分母（MAC 再送カウンタ）の作り方

driot は `Ev= Drop` / `Ev= AckTimeout` の ASCII 出力をコメントアウトしている
（`driot_mac.cpp:2622, 2665`）ため、失敗そのものはトレースに出ない。
そこで送信試行ごとに出る `Ev= Tx-DATA` の `Retry=`（`driot_mac.cpp:2492-2499`）から
「何回目の送信で決着したか」を復元する。

1 フレーム = 1 回の `DataFrameDequeued` + N 回の `Tx-DATA`（再送では dequeue は
出し直されない。`driot_mac.cpp:1633` のガードで早期 return する）。
DrIotMac は outputBuffer を1つしか持たない stop-and-wait なので、1 ノードにつき
ACK 待ちのデータフレームは常に高々1つ。したがって次の `DataFrameDequeued` が来た
時点で、直前のフレームの成否が確定する。

| カウンタ | 条件 | PER の分母 |
|---|---|:--:|
| `macTxSuccessCount` | 再送なし（`Retry= 0`）で ACK が返った | ○ |
| `macRetryCount` | 1 回の再送（`Retry= 1`）で ACK が返った | ○ |
| `macMultipleRetryCount` | 2 回以上の再送で ACK が返った | ○ |
| `macTxFailCount` | `Retry= 3`（= `driot-max-frame-retries`）まで粘っても ACK なし | ○ |
| `macCsmaFailCount` | CSMA バックオフ上限で、**送信すらせず**破棄 | **×** |

`macCsmaFailCount` を分母から外すのは、CSMA バックオフ上限超過による破棄
（`driot_mac.cpp:841-862` の `ProcessCcaFailure`）が `retryTxCount` を進めないまま
（インクリメントは :844 でコメントアウト）フレームを即座に捨てるためである。
これは「電波に出したが届かなかった」ではなく「混んでいて出せなかった」であり、
伝送路の品質を測る PER とは別の現象。

シミュレーション終了時点でまだ ACK 待ちだったフレームも、成否が確定していないので
分母に入れない（`PANn_*_Unresolved` 列に診断値として残る）。

## 3. メトリックの時間分割（このブランチの中核）

IEEE 802.15.4 の標準化文書では、5 つのカウンタを**同時に測定できない**。
そこで 1 メトリックあたり 200 s の窓を順に割り当てる。

```
    0 –   20       ウォームアップ（送信なし）
   20 –  220   W0  macTxSuccessCount
  220 –  420   W1  macRetryCount
  420 –  620   W2  macMultipleRetryCount
  620 –  820   W3  macTxFailCount
  820 – 1020   W4  macRxSuccessCount（= 分子の受信数）
 1020 – 1060       ドレイン
```

したがって td（時間分割）の PER は

```
PER = 1 − Rx(W4) / [ S(W0) + R(W1) + M(W2) + F(W3) ]
```

となる。`macCsmaFailCount` はこの構成では測定しない（窓を持たない）。

### 窓への帰属ルール

| カウンタ | 帰属に使う時刻 |
|---|---|
| tx_success / retry / multi_retry / tx_fail | そのフレームの **`DataFrameDequeued` の時刻** |
| rx_success と RSSI | **`RxFrame` イベントの時刻** |

送信側に dequeue 時刻を使うのは、失敗の確定時刻がトレースに出ないため。
こうすると 4 カウンタが「その窓で開始したフレーム」の綺麗な分割になる。
受信側は dequeue の概念が無いのでイベント時刻を使う。

窓境界をまたぐフレームは stop-and-wait なので 1 ノードあたり境界ごとに高々 1 通で、
総数に対して無視できる。ゲーティングはトレースのタイムスタンプ（`parts[1]`、秒）を
見て後処理で行うので、**driot にも base_simulator にも変更は入っていない**。
フレーム自体は窓に関係なく流れており、変わるのは「数えるかどうか」だけなので、
実機で「その窓ではそのカウンタしか数えていない」状態と等価になる。

## 4. 2 つの測定モード

同じ 1 本のトレースから 2 通りを算出している。

| モード | 測り方 | 列名 | 出力 |
|---|---|---|---|
| **td**（主） | 各メトリックを自分の窓で測る | 既存の列名のまま | `interference_detection_results.csv` |
| **conv**（対照） | 全メトリックを **W0 の 200 s** で同時に測る | 既存の列名 + `_conv` | `..._conv.csv` |

```sh
python3 script/analyze_csv.py    --mode td     # 既定
python3 script/analyze_csv.py    --mode conv
python3 script/create_heatmap.py --mode conv
```

conv に W0 を使うのは現行設定（20–220 s）をそのまま再現するため。
**1 メトリックあたりの観測時間が両モードで等しい（200 s）**ので、
時間分割そのもののコストだけを分離できる。

## 5. 既知の性質と注意点

### 構造的に PER ≥ 0 が保証されない

分母は「決着のついた**フレーム数**」だが、分子の受信数は `Ev= RxFrame` を
**1 行ごとに数えたもの**で、**再送フレームの重複受信もそのまま加算される**。
ACK だけが失われて再送された場合、受信側は同じフレームを複数回受け取る。

さらに td では分子（W4）と分母（W0–W3）が**互いに素なフレーム集合**なので、
`受信数 ≤ 分母` という関係に構造的な根拠が無い。

実装では `[0, 1]` にクリップし、**クリップが起きた件数を必ず標準出力に出す**。

```
--- PER clip: 受信数 > 分母 となり 0 にクリップした件数 N / M (x.xx%) ---
```

**実データを解析したら、まずこの率を確認すること。** 率が高ければ、この PER 定義は
ACK 損失を損失として捉えられていない。

### td では PER が「割合」ではなく「2 つの独立な推定値の比」になる

| | 分子 | 分母 | 関係 |
|---|---|---|---|
| conv | Rx(W0) | S+R+M+F(W0) | 同じ窓の同じフレーム集合。分母は確定値で、比は正真正銘の割合 |
| td | Rx(W4) | S(W0)+R(W1)+M(W2)+F(W3) | 互いに素なフレーム集合。分子と分母が独立で、分母自体も確率変数 |

これにより PER 推定の分散が増える。

```
conv:  Var(PER) = p(1-p) / N
td  :  Var(PER) = [ p(1-p) + (1-p)^2 (1 - Σpx^2) ] / N        px = ps, pr, pm, pf
```

| PER | conv の係数 | td の係数 | 分散比 |
|---:|---:|---:|---:|
| 0.05 | 0.0475 | 0.2154 | 4.5 |
| 0.10 | 0.0900 | 0.3055 | 3.4 |
| 0.20 | 0.1600 | 0.4571 | 2.9 |

検知統計量はビン内 ΔPER の分散なので、帰無水準 τ はこの分散に比例して上がる。
**実測では τ が 0.0260 → 0.0490（1.88 倍）、F1 中央値が 0.912 → 0.769（−0.104）**
となっており、真の端末間ばらつき σ²_het は変わらずノイズ項だけが 3〜4 倍に
なった、という説明と整合する。これは実装の誤りではなく、標準の制約がもたらす
本質的なコストである。

### 旧 PER（受信数ベースではない定義）の残骸

`PANn_PC_NoAck_to_Dev{d}` / `PANn_Dev{d}_NoAck` 列は、受信数ベースに置き換える前の
PER の分子（dequeue したが最後まで ACK が返らなかった数）である。
現在の解析では使っておらず、時間分割の対象外として全区間で数えたままにしてある。

### 参考：`one_side_correct_measure` との違い

あちらの `create_csv.py` には**時間ゲートが一切なく、トレース全体
（20–260 s、ドレイン 40 s 込み）を数えていた**。「200 s 測定」と呼んでいたものは
実際には約 240 s だった。本ブランチの conv は 20–220 s ちょうどなので、
**conv のほうが測定として正確**である。

## 付録：クリップ率の診断（`script/diagnose_per_clip.py`）

### 背景

実データで **クリップ率 9.50%（342,042 / 3,599,932）** が観測された。
「約10回に1回、PER が負になって 0 に潰されている」という状態で、
統計量の分子を直接汚染する。原因の切り分けが必要。

当初は「受信数に再送フレームの重複が混ざっているため」と考えたが、
**これは誤りだった**。driot は重複受信を `Ev= RxDupFrame` という別イベントで
出力しており（`driot_mac.cpp:2598`、`ProcessDataFrame` の else 側 :2770）、
`create_csv.py` のイベント分岐は完全一致なので最初から数えていない。

### 想定される機序

分母は「dequeue されたフレーム数」ではなく、そこから `macCsmaFailCount` を
除いた数である。

```
分母 = macTxSuccess + macRetry + macMultipleRetry + macTxFail
     = dequeue 数 − csma_fail − unresolved(1ノードあたり高々1)
```

一方 `ProcessCcaFailure`（`driot_mac.cpp:841`）は **再送の途中でも**
バックオフ上限超過でフレームを破棄し、しかも `retryTxCount++` が
コメントアウトされているため `Retry=` が進まない。その結果
`create_csv.py` は `max_retry < MAX_FRAME_RETRIES` と見て `csma_fail` に
分類する。**一度は電波に出て受信側に届いているのに分母から外れる**経路が存在する。

td ではさらに、分子 Rx(W4) と分母 S(W0)+R(W1)+M(W2)+F(W3) が
**互いに素なフレーム集合**になるため、包含関係そのものが無い。定常なら

```
PER = 1 − (1 − PER_frame) / (1 − p_csma)
```

となり、**`PER_frame < p_csma` のとき負**になる。

### 予測

| | 予測 |
|---|---|
| 自PAN負荷 | 低負荷では `p_csma ≈ 0` なのでクリップしない。**高負荷に集中** |
| RSSI | 強い端末ほど `PER_frame ≈ 0` なので、わずかな `p_csma` でも負になる。**強いビンに集中** |
| td vs conv | conv は同一窓なので概ね包含が成り立つ。**conv のほうが大幅に低い** |

### 診断スクリプトが出すもの

```sh
python3 script/diagnose_per_clip.py              # td と conv の両方
python3 script/diagnose_per_clip.py --mode conv  # 片方だけ
```

1. モード別の全体クリップ率
2. 自PAN負荷別のクリップ率
3. RSSI ビン別（起点からの相対位置）のクリップ率
4. 方向（UL / DL）別のクリップ率
5. `macCsmaFailCount` の割合（自PAN負荷別）
6. `WindowDeq_*` の均衡（トラフィックが定常か）
7. **分母に `macCsmaFailCount` を含めた場合のクリップ率** ← 修正案の効果を直接測る

出力は標準出力のサマリと `plots/per_clip_diagnosis.csv`。

### 切り分けの読み方

| 結果 | 結論 |
|---|---|
| conv のクリップ率がほぼ 0% | 窓の分割が主因。td 固有 |
| conv も 9% 前後 | `csma_fail` の除外が主因。両モード共通 |
| 分母に csma_fail を含めるとクリップが消える | **修正案が有効**。`_one_side_per` に1項足すだけ |
| 高負荷・強RSSI に集中している | 上の機序の裏付け |
| `WindowDeq_*` が揃っていない | トラフィックが非定常で、分母の期待値がずれている |
