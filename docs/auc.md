# AUC

干渉検知の性能を、閾値の選び方に依らない形で測る。実装は
`script/analyze_csv.py::_rank_auc()`。全体の構成は `docs/README.md` を参照。
ここは AUC に絞った詳細。

---

## 1. なぜこのブランチは AUC だけなのか

`save` ブランチは F1 と AUC の両方を出していた。F1 は**閾値 τ を 1 点に決めたときの
性能**で、`VARIANCE_THRESHOLDS`（0.000〜1.000 を 0.001 刻み）を全部試して F1 が
最大になる τ を選ぶ、という作りだった。

このブランチが F1 を落としたのは、**3手法のスコアに共通の閾値グリッドが引けない**
ためである。

| 手法 | スコア | 単位 | 値域 |
|---|---|---|---|
| `proposed` | RSSIビン内 ΔPER 分散の最大値 | 無次元 | `[0, 1]` |
| `dper` | 全端末の ΔPER 分散 | 無次元 | `[0, 1]` |
| `rssi` | 全端末の平均 RSSI | dBm | 負の実数（実測 -60 前後） |

`0.000〜1.000 を 0.001 刻み` は `rssi` に対しては全く意味を成さない。手法ごとに
別のグリッドを用意すれば数字は出るが、「グリッドの切り方が違う3つの F1」を
並べることになり、比較として成立しない。

AUC は τ を決めず、**スコアの分離度そのもの**を測る。順位しか見ないので
**単調変換に不変**であり、単位も値域も違う統計量を同じ土俵で比べられる。
これがこのブランチで AUC だけを使う理由である。

（F1 そのものにも「干渉の有無を知った上で最適化しているので楽観側に偏った上限に
なる」「グリッドの刻みに依存する」という性質があった。`save` の `best_threshold` は
0〜0.143 にしか分布しておらず、0.001 刻みでは候補が実質 143 通りしかなかった。）

## 2. 入力になるスコア

AUC は 2 クラスの分離度なので、まず「干渉あり」「干渉なし」の 2 群のスコアを作る。

ある条件（帯域ペア, 距離, 両PANの負荷, どちらの PAN から見るか, **どの手法か**）に
ついて、Seed ごとに1つのスカラーを計算する（`compute_seed_scores()`）。手法ごとの
中身は:

| 手法 | Seed ごとの計算 |
|---|---|
| `proposed` | ΔPER を取る → RSSI でビン分け（起点 = 受信感度 + 3 dBm、幅 10 dBm）→ ビンごとに ΔPER の分散 → その Seed 内での最大値 |
| `dper` | ΔPER を取る → 全端末で分散（ビン分けしない） |
| `rssi` | 全端末の平均 RSSI |

どれも `ΔPER = PER_DL − PER_UL`、対象は `RSSI != 0` の端末で共通。

これを Seed 100 本ぶん繰り返すと、手法ごとに長さ 100 の配列が 2 本できる。

| 変数 | 中身 | ラベル |
|---|---|---|
| `interf_values` | 同一周波数ペア（ch 0–2 どうし）の 100 Seed | 陽性 |
| `no_interf_values` | 別周波数ペア（ch 0–2 vs 3–5）の 100 Seed | 陰性 |

対になるのは**同じ帯域・同じ負荷で、干渉の有無だけが違う**条件同士。
対応づけは `run_interference_detection()` が `get_interf_label()`
（2つのチャネルの周波数が一致すれば `interf`）で行う。手法ループはその内側にあり、
**3手法は同じ ΔPER 配列・同じ RSSI 配列から作られる**（手法ごとに
`load_and_aggregate()` からやり直すと 155MB を3回読むことになるため）。

スコアそのものは `plots/detection_scores_simultaneous.csv` に残してある
（300 セル × 200 Seed × 3 手法 = 180,000 行）。検知結果 CSV は手法ごとに AUC という
1つの要約しか持たないので、分布を見直したくなったときのため。これを残しておけば
155MB の `simulation_results.csv` を再解析せずに済む。

## 3. AUC の定義と実装

```
AUC = P(指標_interf > 指標_no_interf) + 0.5 × P(同値)
```

陽性と陰性から 1 つずつ無作為に取り出したとき、陽性のほうが大きい確率。
同値は 0.5 と数える。ROC 曲線の下側面積と数学的に一致する（Mann–Whitney U と等価）。

- 1.0 = 完全に分離
- 0.5 = ランダムと同じ
- 0.0 = 完全に逆転

```python
def _rank_auc(interf_values, no_interf_values):
    n_pos = len(interf_values)
    n_neg = len(no_interf_values)
    if n_pos == 0 or n_neg == 0:
        return float("nan")

    ranks = stats.rankdata(np.concatenate([interf_values, no_interf_values]))
    return (ranks[:n_pos].sum() - n_pos * (n_pos + 1) / 2.0) / (n_pos * n_neg)
```

3 段階になっている。

**(a) 2 群を連結して通し順位を振る。** 陽性を前半に置くので `ranks[:n_pos]` が
陽性側の順位になる。

**(b) 陽性側の順位和から最小値を引く。** 陽性が全部最下位なら順位は 1…n_pos で
和は `n_pos(n_pos+1)/2`。これを引いた残りが **U 統計量**で、「陽性が最低ラインから
どれだけ上に押し上がっているか」を表す。

**(c) 最大値 `n_pos × n_neg` で割る。** 陽性が全部陰性より上のときの U がこれ。

### 手計算の例

陽性 `[0.05, 0.02, 0.09, 0.02]`、陰性 `[0.01, 0.02, 0.03]`:

```
値    0.05  0.02  0.09  0.02 | 0.01  0.02  0.03
順位  6.0   3.0   7.0   3.0  | 1.0   3.0   5.0     ← 0.02 が3つ → midrank 3.0

陽性の順位和 R = 6.0 + 3.0 + 7.0 + 3.0 = 19.0
U   = 19.0 − 4×5/2 = 9.0
AUC = 9.0 / (4×3) = 0.75
```

12 通りの総当たりで「勝ち + 0.5×引き分け」を数えても 9.0/12 = 0.75 で一致する。

### 向きを補正していない

判定は「値が大きいほど干渉あり」で片側固定（`METHOD_SIGN` が3手法とも `+1`）
なので、AUC の向きも一意に決まる。

`max(auc, 1 − auc)` のような補正はしない。**0.5 を下回ったら「指標が干渉の有無と
逆相関している」という情報そのもの**で、補正するとそれが潰れるため。

これはベースラインにも等しく適用される。特に `rssi` は「干渉で弱い端末のフレームが
落ちるぶん、受信できたフレームの平均RSSIが上振れする」という**想定**で `+1` に
置いているだけなので、想定が外れていれば 0.5 を割る。それを `max(auc, 1-auc)` で
0.5 以上に持ち上げると、**ベースラインが実際より強く見える**。比較の公平さは
「両方向を試して良いほうを採る」ことではなく、「3手法とも同じ規則で扱う」ことで
担保する。向きを変える判断をしたくなったら `METHOD_SIGN` の1行だけを `-1` にする
（コードが自動で決めてはいけない）。

### 同値の扱い

`rankdata` は同順位に **midrank**（平均順位）を与えるので、同値ペアが自動的に
0.5 として数えられ、定義式の `+ 0.5 × P(同値)` が再現される。

同値が出る経路は実在する。スコアを作れなかった Seed に
`compute_seed_scores()` が `METHOD_DEGENERATE_SCORE` をそのまま入れるため
（`proposed` なら有効ビン（端末 2 個以上）が 1 つも作れなかったとき）。
`save` の実データでは退化 Seed は 0 件だった（CSV の `n_degenerate_*` 列）。

### 端のケースと丸め

- どちらかの群が空なら `nan`。実データでは常に 100 Seed ずつなので起きない。
- CSV には**小数 4 桁**で書く。100×100 = 10,000 ペアなので刻みが 1e-4 であり、
  それ以上の桁に意味が無い。

### 依存

`scipy.stats` は元から import 済みなので新しい依存は無い。sklearn は実装には
使わず、検証でのみ使う。

## 4. 検証

`_rank_auc()` は `save` から1文字も変えていない。`save` の実データ
（sequential/simultaneous 各 300 セル、各セル 100+100 Seed）で以下を確認済み。

| 検証項目 | 結果 |
|---|---|
| `_rank_auc` vs `sklearn.roc_auc_score` | 600 セル全て一致（最大誤差 2.2e-16） |
| `_rank_auc` vs ROC 曲線の台形則面積 | 600 セル全て一致（最大誤差 2.2e-16） |
| 検知結果CSVの `auc` 列 vs 再計算 | 600 セル全て一致（4桁丸めの範囲） |
| `own_other()` のキー一意性 | 45 キー、衝突 0（スコアが混ざる事故が無い） |
| 折れ線の描画値 vs CSV | 90 点全て一致 |

単体では境界ケース（完全分離・完全逆転・全同値・同値多数・片側1要素）と
同値を多く含むランダム 200〜300 ケースでも sklearn と一致を確認している。

3手法化のリファクタ（`compute_seed_max_variance()` → `_iter_seeds()` +
`_score_proposed()` + `compute_seed_scores()`）については、合成した
`simulation_results.csv` を `save` と `icc` の両方の `analyze_csv.py` に通し、
**`proposed` の `auc` が完全に一致する**ことを確認してある。
ビン構成の診断値（`BIN_OCCUPANCY` / `DEGENERATE_SEEDS`）も一致する
―― 3手法ぶん回しても `proposed` のときしか集計しないため、同じ Seed を
3回数える事故は起きない。

## 5. 実データの読み方（`save` の提案手法のみ）

以下は `save` ブランチで提案手法1つを評価したときの値。**3手法比較の数字は
`icc` でシミュレーションを回した後に入る。** 提案手法の傾向を読む参考として残す。

### 全体

| | AUC 中央値 | F1 中央値 |
|---|---|---|
| simultaneous | **0.966** | 0.912 |
| sequential | **0.824** | 0.769 |

### 自PAN負荷が上がると落ちる

自PAN負荷別の AUC 中央値:

| 自PAN負荷 | simultaneous | sequential |
|---:|---:|---:|
| 20% | 0.998 | 0.897 |
| 40% | 0.996 | 0.900 |
| 60% | 0.990 | 0.860 |
| 80% | 0.931 | 0.799 |
| 100% | 0.887 | 0.751 |

自分のトラフィックが増えるほど、自PAN内の輻輳由来のばらつきが相手の干渉の
痕跡を覆い隠す。

### AUC < 0.5 のセル

sequential で 6/300、simultaneous で 1/300。**7 件すべてで相手PAN負荷が 20%** だった。

```
自100kbps 相200kbps  自負荷100% 相負荷 20%  AUC 0.4705   (sequential)
自200kbps 相100kbps  自負荷100% 相負荷 20%  AUC 0.4775   (sequential)
自100kbps 相 50kbps  自負荷 60% 相負荷 20%  AUC 0.4797   (sequential)
...
自100kbps 相 50kbps  自負荷100% 相負荷 20%  AUC 0.4762   (simultaneous)
```

相手がほとんど送信していないので**検知すべき干渉が実質存在せず**、2 群が区別
できない。AUC は 0.5 近傍に張り付き、ノイズで下側に振れたものが 0.5 を割る。
異常ではなく、そういう条件だというだけ。

**折れ線の図にはこれらは出ない。** 図は相手負荷 100% の断面に固定しているため。
ベースライン（特に `rssi`）はこれと違い、相手負荷 100% の断面でも 0.5 を割り得る
（それが §3 の「向きを補正していない」が効く場面で、y 軸の下端が自動で下がる）。
